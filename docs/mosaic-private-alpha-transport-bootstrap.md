# Mosaic Private-Alpha Transport Bootstrap.1

Status: implemented package contract for the internal macOS private alpha as of 2026-08-21. Application-owned encrypted persistence, a concrete Tor-only WebSocket adapter, circuit-isolation evidence, and the complete G2 application rehearsal remain required before G2 can close.

Contract identifier: `nostr-tor/0-opal-mosaic-private-alpha-bootstrap.1`.

Nostr routing selector: `nostr-tor/0-opal-mosaic-boot.1`.

This contract fills the authenticated mailbox-distribution boundary between one complete `nostr-tor/0-opal-mainnet-alpha-private-deployment.1` formation and the existing `nostr-tor/0-opal-mainnet-alpha.5` post-manifest runtime. It does not alter the bytes, enums, deadlines, roles, relay set, or authority of private-deployment.1, `Mosaic/0-opal-mainnet-alpha.4`, or alpha.5. Any incompatible bootstrap change requires a new bootstrap identifier and Nostr selector.

## 1. Context And Sequence

Bootstrap begins only after OpalFusion has authenticated one complete private-deployment proof and ends no later than that manifest's wallet-reservation deadline. Every standalone document binds the alpha.4 profile, alpha.5 transport profile, private-deployment.1 selector, mainnet genesis hash, exact round identifier, exact relay-set digest, post-manifest phase start, and wallet-reservation deadline.

The exact minimum-roster sequence is:

1. The application gives every roster member one freshly generated control-mailbox recipient key that is distinct from every discovery key, roster control key, other control-mailbox key, anonymous-return key, anonymous recipient key, wallet key, and wrapper key.
2. The conductor creates one fresh, attempt-exclusive RSA-2048 RSABSSA signing capability for this exact attempt and signs its RFC 9474 verification-key document with the manifest conductor control key. Its application-owned `SecKey` persists only inside the authenticated attempt state until authorized cleanup. Restoration must match the exact frozen verification key; generating a replacement is forbidden.
3. Each contributor creates one fresh anonymous-return identity and one recoverable blind request over an attempt-bound authorization input containing the authorization-key identifier, one fresh 32-byte nonce, and that anonymous-return identity. Only the blinded 256-byte message enters the contributor's control-mailbox claim. The conductor claim contains no blind request.
4. Each roster member signs one control-mailbox claim with its existing roster control key. Each member publishes that same signed claim to every other roster control identity through a distinct fresh NIP-59 wrapper. A member combines the six authenticated remote claims with its local claim; canonical claim-set order is control-key byte order and is independent of relay arrival order.
5. The conductor blind-signs exactly one request for every contributor and signs the complete response set with its control key. Each contributor selects its response by control identity, byte-matches the blinded request in its own claim, restores or retains the exact blind-request state, finalizes the blind signature, and verifies the resulting RFC 9474 token.
6. Each contributor redeems that token in one registration signed by its anonymous-return key and delivers it to the conductor control mailbox from that same anonymous identity. The registration contains no contributor control identity, mailbox recipient identity, or mailbox private key. The conductor rejects a duplicate authorization spent identifier or anonymous-return identity through its durable attempt ledger.
7. For each accepted anonymous registration, the conductor generates exactly 23 fresh anonymous recipient keys locally, retains their private capabilities locally, signs an assignment containing only the 23 public recipient identities and their bundle commitment, and delivers that assignment to the registration's anonymous-return identity. No mailbox private key crosses the protocol boundary.
8. After accepting exactly six unique registrations and assignments, the conductor signs one sorted, unlabeled set containing only the six mailbox-bundle commitments. Every contributor verifies that its local assignment commitment is present. Every roster member durably reserves that exact registration-set digest, signs only that common digest with its control key, and refuses to sign a different digest for the same round. The complete acknowledgement set contains exactly one valid acknowledgement for every roster control identity.
9. OpalFusion mints the sole post-manifest mailbox capability only after the complete acknowledgement barrier. A contributor receives the 23 public anonymous recipient keys from its own assignment. The conductor receives all 138 corresponding private recipient capabilities, sorted by public event identity. No caller may directly construct the production mailbox capability around partial or unauthenticated state.

Missing, extra, duplicate, differently bound, expired, noncanonical, incorrectly signed, already spent, split-view, or identity-reusing state is terminal for this bootstrap attempt. There is no clearnet, side-channel, partial-roster, guessed-key, regenerated-key, or second-runtime fallback.

RFC 9474 blindness removes an explicit conductor-visible mapping between a contributor control identity and its redeemed anonymous-return identity. It does not prove that timing, relay, Tor-circuit, host, or traffic metadata cannot correlate them; those remain deployment and G4 review obligations.

## 2. Canonical Documents

All integers and vectors use the repository's strict canonical encoder and consume their complete input on decode. Every standalone transported document is nonempty and at most 4,092 bytes. The locally reconstructed complete claim set is bounded separately at 65,536 bytes because the seven individually transported claims can exceed one padded NIP-59 payload; the aggregate claim set is never transported as one bootstrap rumor.

The common signed-document prefix is `text(bootstrapIdentifier) || text(privateDeploymentIdentifier) || text(alpha4Profile) || text(alpha5TransportProfile) || mainnetGenesisHash32 || roundIdentifier32 || relaySetDigest32 || phaseStart u64 || walletReservationDeadline u64 || documentKind u8`. Document kinds are authorization key `0`, control-mailbox claim `1`, blind-response set `2`, anonymous registration `3`, anonymous assignment `4`, registration set `5`, and registration-set acknowledgement `6`.

The authorization-key body appends `bytes(rsaSubjectPublicKeyInfo)`. The manifest conductor control key signs `SHA256("Mosaic/private-alpha-transport-bootstrap.1/authorization-key" || canonicalBody)`. Its document digest uses the `authorization-key-document` domain suffix.

A control-mailbox claim body appends `authorizationKeyDocumentDigest32 || rosterControlIdentity32 || freshControlRecipientIdentity32 || requestFlag u8 || blindedMessage256?`. The conductor flag is zero and has no blinded message; every contributor flag is one and has exactly one blinded message. The roster control key signs the `control-mailbox-claim` domain hash. The complete claim set is `text(bootstrapIdentifier) || roundIdentifier32 || relaySetDigest32 || authorizationKeyDocumentDigest32 || vector(bytes(canonicalClaim)...)` with exactly one valid claim for every roster member in control-key byte order. Its digest uses the `control-mailbox-claim-set` domain suffix.

The blind-response-set body appends `authorizationKeyDocumentDigest32 || claimSetDigest32 || vector(contributorControlIdentity32 || blindSignature256...)` in contributor-control-key order. It contains exactly one response for every contributor and is signed by the manifest conductor over the `blind-response-set` domain hash. Its document digest uses the `blind-response-set-document` suffix.

The blind authorization input is `text(bootstrapIdentifier) || roundIdentifier32 || relaySetDigest32 || authorizationKeyIdentifier32 || authorizationNonce32 || anonymousReturnIdentity32`. Its spent identifier is the `anonymous-mailbox-authorization-spent` domain hash of those exact bytes. The recoverable OpalCrypto blind-request state is fixed-width, message- and verification-key-bound secret state; it never enters a claim, response, registration, diagnostic, or public document.

The anonymous-registration body appends `authorizationKeyDocumentDigest32 || claimSetDigest32 || responseSetDigest32 || bytes(canonicalAuthorizationInput) || messageRandomizer32 || finalizedRSABSSASignature256`. The anonymous-return key signs the `anonymous-mailbox-registration` domain hash. The loader verifies the RFC 9474 token and the BIP-340 signature before exposing a registration. Its document digest uses the `anonymous-mailbox-registration-document` suffix.

The anonymous-assignment body appends `registrationDigest32 || anonymousReturnIdentity32 || mailboxBundleCommitment32 || vector(anonymousRecipientIdentity32...)` with exactly 23 public recipient identities. The manifest conductor signs the `anonymous-mailbox-assignment` domain hash. The commitment is the `anonymous-mailbox-bundle` domain hash of the ordered 23-identity vector. Conductor restoration requires byte-exact correspondence between those public identities and the separately persisted private recipient capabilities.

The anonymous-registration-set body appends `authorizationKeyDocumentDigest32 || claimSetDigest32 || responseSetDigest32 || vector(mailboxBundleCommitment32...)`. It contains exactly six unique commitments in byte order, contains no registration digest, anonymous-return identity, recipient identity, or control identity, and is signed by the manifest conductor over the `anonymous-mailbox-registration-set` domain hash. Its document digest uses the `anonymous-mailbox-registration-set-document` suffix.

An acknowledgement body appends `registrationSetDigest32 || rosterControlIdentity32`. The roster control key signs the `registration-set-acknowledgement` domain hash. A contributor may create this signature only after local assignment inclusion; the conductor has no local assignment. The complete acknowledgement set is `text(bootstrapIdentifier + "/acknowledgement-set") || roundIdentifier32 || relaySetDigest32 || registrationSetDigest32 || vector(bytes(canonicalAcknowledgement)...)` with exactly one acknowledgement for every roster member in control-key order.

Control recipient identities, anonymous-return identities, and anonymous recipient identities are globally unique and disjoint from every pre-manifest discovery and roster control identity. Anonymous recipient identities are additionally disjoint from every control recipient and every anonymous-return identity. Blinded requests, authorization spent identifiers, registrations, assignments, bundle commitments, and wrapper identities are unique within one attempt.

## 3. NIP-59 Mapping

Each standalone bootstrap document is encoded as the existing exact 8,192-byte padded application content in an unsigned kind-78 rumor. The rumor has exactly one tag `["d", "nostr-tor/0-opal-mosaic-boot.1"]`. The descriptive bootstrap identifier remains inside the signed canonical document; the shorter routing selector keeps the already frozen alpha.5 rumor, seal, gift-wrap, and publication ceilings unchanged.

Authorization keys, blind-response sets, anonymous assignments, registration sets, and complete acknowledgement sets are authored by the conductor. Control claims and individual registration-set acknowledgements are authored by the applicable roster control key. An anonymous registration is authored by its anonymous-return key. Claims, authorization responses, registration sets, acknowledgements, and acknowledgement sets use control-mailbox recipients. Anonymous registrations target the conductor control mailbox. Anonymous assignments target the exact anonymous-return identity. The authenticated NIP-59 rumor sender must equal the signed canonical document's required author.

The outer event is a regular kind-1059 gift wrap with exactly one `p` tag, the existing alpha.5 fixed ciphertext sizes, and one caller-supplied fresh wrapper key. Phase-start, rumor, seal, gift-wrap, current-time, and wallet-reservation bounds use the existing strict alpha.5 ordering.

Before sealing, the application supplies the complete persisted event-identity reservation set for the attempt, including every previously minted wrapper. OpalFusion combines it with the authenticated identities known at that boundary and rejects any malformed or reused wrapper identity. The application atomically persists the newly sealed canonical event, canonical document, operation identifier, and wrapper identity before route provisioning. The operation identifier hashes the exact attempt/generation/material binding, authenticated sender, recipient, canonical-document digest, canonical-event digest, and three endpoint digests. Recovery requires that stored identifier to match, restores the exact signed event bytes without retaining the ephemeral wrapper secret, and never reconstructs or rewraps an already sealed publication.

Inbound validation can prove that a received wrapper differs from the sender, recipient, pre-manifest identities, and the recipient's known bootstrap identities. It cannot prove that a remote sender never reused that wrapper in an unseen attempt; outbound durable reservation and cross-attempt erasure policy remain application evidence.

## 4. Relay Policy, Publication, And Inbox

The application canonicalizes one fresh opaque pool identifier and exactly three reviewed relay registrations before discovery. Endpoint normalization, distinct endpoint and operator identities, `wss`-only policy, and rejection of NIP-42 or relay proof-of-work requirements remain the private-deployment.1 rules. The complete manifest proof supplies the authoritative normalized endpoint identifiers; bootstrap cannot substitute another endpoint set.

For each requested endpoint the application provisions one concrete Tor-only WebSocket capability, one distinct circuit-isolation identifier, and one distinct connection object. OpalFusion rejects a missing, extra, duplicate, substituted, or shared route and closes every rejected connection. An initial outbound publication targets all three exact endpoints. A relay acceptance counts only after the application durably records that endpoint against the publication operation identifier. Fewer than two durable acceptances fails closed. Recovery reloads durable acceptances and republishes the byte-identical event only to unaccepted endpoints; an already durable two-relay quorum opens no route.

An inbound bootstrap inbox subscribes all three exact sources before returning its bounded event stream. It accepts only the exact recipient identity, canonical signed event bytes, and a bijective wrapper-identity/message-identifier replay fact. Identical relay copies produce one event. A wrapper identity associated with another message, a message identifier associated with another wrapper, bounded-buffer loss, subscription closure, acknowledgement on the subscription stream, connection completion, or any source loss terminalizes the inbox and closes all routes.

Reconnect constructs a new inbox from the complete durably stored replay entries. The application persists each replay entry before opening the contained bootstrap document or applying semantic state. A duplicate after reconnect is ignored; a conflicting replay fact fails before semantic admission.

## 5. Application Durability And Secret Lifecycle

The G2 application record must extend the G1 authenticated outer attempt record under the same cross-process lock and compare-and-replace revision. At minimum it retains the canonical relay and pool documents, exact deployment proof or its existing recovery bytes, local control-mailbox private key, local claim, complete claim set, role-appropriate authorization state, sealed outbound publications, reserved event identities, durable per-endpoint acceptances, inbound replay entries, subscription identity inputs, and current bootstrap phase.

Contributor state additionally retains the authorization nonce, encrypted OpalCrypto blind-request recovery state until successful redemption, anonymous-return private key, registration, assignment, chosen registration-set digest, and complete acknowledgement set. Conductor state additionally retains the app-owned RSA `SecKey`, its exact verification-key document, a durable authorization-spent-identifier-to-registration-digest ledger, every accepted registration, each assignment's locally generated 23 private recipient capabilities, the common registration set, and the complete acknowledgement set. A conductor replay of the same registration digest is idempotent; the same spent identifier with another digest is terminal. A roster member must atomically compare-and-set its first acknowledged registration-set digest and must never sign a different digest for the same round.

Private recipient capabilities remain conductor-local and are never serialized into a bootstrap canonical document, NIP-59 rumor, relay frame, or diagnostic. Raw blind-request recovery state, RSA private material, control recipient keys, anonymous-return keys, and wrapper keys are likewise secret-bearing. Application persistence must authenticate and encrypt them, bind them to the outer attempt revision, and read back the committed value before the corresponding protocol action becomes externally visible.

No raw secret, relay endpoint, SOCKS credential, wallet linkage, amount, outpoint, address, script, registration-to-control mapping, or stable cross-attempt identifier belongs in diagnostics. Terminal cleanup follows the G1 erasure authority: stop and join every route and inbox, delete the complete authenticated outer record and Keychain material through the existing authorized cleanup path, retain only the allowed tombstone or operator evidence, and never erase while wallet or chain disposition is uncertain.

## 6. Concrete Tor Requirement

The package contract deliberately receives route capabilities rather than constructing a network stack. G2 application evidence must show that the production adapter uses secure WebSockets through a locally configured Tor SOCKS5 proxy with remote name resolution, failover disabled, no direct URLSession or Network fallback, and distinct SOCKS authentication credentials or an equivalent reviewed `IsolateSOCKSAuth` mechanism for every route. The exact three manifest endpoints must map to three independently reviewed operator entries and three distinct route capabilities.

A local loopback harness must exercise the production adapter, SOCKS negotiation, WebSocket publication, two-of-three durable acknowledgement, three-source subscription, deduplication, reconnect, source loss, bounded shutdown, and secret cleanup in less than 30 seconds without an external relay or BCH network. External staging remains a separately approved action and cannot replace the loopback proof.

## 7. Non-Proofs And Disable

Relay acknowledgements are not durable delivery to every participant, circuit independence, operator independence beyond the reviewed registry assertion, anonymity, traffic-analysis resistance, Sybil resistance, wallet safety, broadcast permission, or chain acceptance. Blind authorization prevents the protocol transcript from directly labeling a registration with a control identity; it is not a proof against timing or network correlation. Complete roster acknowledgements prevent a successfully acknowledged split view only when every participant durably enforces the single-digest signing rule. Scripted package tests do not prove the concrete Tor adapter or application persistence.

The feature remains structurally disabled until G2 and G3 evidence bind this contract to the exact promoted dependency graph and one supervised application owner. Rollback is to disable private discovery, stop and join bootstrap routes, preserve the authenticated G1/G2 record and wallet quarantine until exact disposition is known, and invoke the existing terminal cleanup authority only when package and application evidence permit it. No failure enables clearnet, a different relay, regenerated attempt material, a second runtime constructor, broadcast, or value movement.
